5. 三个关键问题的回答

Q1：上游没有持久化+预修复，如何让 hermes CLI 工作？

对照 paperclipai/paperclip @ master（d14a3b88b1）逐字节核对：managedAiHomeEnvironment（含 HERMES_HOME=providerHome）、mkdtemp 一次性 home、AI_AUTH_ENV_KEYS 清空列表 —— 与本地完全一致（上游只是把该函数重构到了 adapter-utils/managed-ai-runtime-env.ts 共享模块）。

上游并没有解决这个组合：hermes CLI lane + 托管连接是本地 AMB-273 线的新能力，上游主要走 ACP lane（长驻暖会话，自举一次后终身复用）。上游若踩到 CLI lane + 托管组合会遇到同样问题。

Q2：pilibala dev 基底版本为什么可以工作？

managed connections 是上游 2026-09-12 引入的功能（#13247），基底（4e715eb7ea）已有同款 home 机制。基底时代工作的 hermes CLI agent 走的是非托管路径：无托管绑定时 HOME 不被重定向 → 数据根 = 宿主 ~/.hermes（owner 根，venv 早已存在，pm.venv_is_current 直接通过）→ 零自举、秒级启动。

即："可以工作"的是非托管 CLI；托管 CLI 组合在基底上从未被行使，本线首次大规模使用即暴露此问题。

Q3：为什么判断持久化+预修复是最应该采用的方式？

候选方案评估结论
env 直供 + 宿主数据根（不设 HERMES_HOME）实测可行（env 注入凭据 + -m + --provider 成功）；但丢失配置隔离：多 provider/自定义网关的投影 config 无处安放，且 hermes 的 provider 解析依赖 config.yaml 的 model 块仅适用单 provider 场景，放弃
venv 克隆/硬链接绕过 sync对抗 hermes pm 的账本/提交语义（committed environment 有代际校验），克隆件会被 venv_is_current 判定为过期，属于 hack放弃
持久 home per grant + 预修复与 hermes 自身模型同构（PM 的设计就是 per-root committed environment，根持久则环境一次提交终身复用）；预修复用的是 CLI 自己提示的官方式（hermes pm repair）；凭据仍然每运行刷新（env 注入），home 内无凭据材料（api_key 路径）采纳

判断依据：① 实测 18:17 沙箱内 sync 可完整成功（1.2GB venv 装好），证明失败点在"每次从零"而非"sync 本身"；② /proc/pid/environ 捕获确认子进程数据根；③ 手动 pm repair 前台复现成功，且 CLI 的报错文本自指该命令；④ 隔离/worktree/续传场景：会话状态随持久 home 存续，续传不再因一次性沙箱消失而产生 internal error（此前 sandbox 日志中的 StateDbReplacedError 即 home 被回收所致）。
