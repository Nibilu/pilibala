# Pilibala alpha 0.0.11 升级说明

**主题：受管 AI 连接（managed AI connection）运行时工程化加固**
**日期：2026-11-17 ｜ 验收：AMB-305 双消息实测全绿**

---

## 一、本版解决了什么

0.0.10 → 0.0.11 期间，所有 `hermes_local engine=acp` agent（acp-dpsk、test、Hermi ACP）的 chat/task 出现多类失败。根因分四层，本版全部修复或显式隔离：

### 1. 一击即溃：`ReferenceError: model is not defined`（致命，已修复）
`buildHermesAcpConfig` 中一处未完成的手工编辑引用了未定义的 `model` 变量，导致**每次** engine=acp 运行在适配器配置构建阶段即死（0 字节日志、2 秒内失败）。
**修复**：恢复被覆盖的 `const model = firstNonEmptyString(config.model) ?? "";` 声明行。
**教训**：失败始于重启边界且无日志时，先查未提交工作区改动，再谈引擎理论。

### 2. 孤儿 socket：聊天"隔条成功"的真根因（已修复）
持久 home 内的 gateway daemon 由首个 run 的子进程孵化，control socket 继承该 run 的 `TMPDIR`；run 结束后临时目录被清理 → **socket 消失而 daemon 存活** → 同 grant 的后续 run 全部等满 60s 截止后失败，直到 daemon 600s 空闲自杀。
**关键陷阱**：home 根下的 XDG 锚点（`<home>/xdg-runtime`）虽然正确创建，但其路径含两个 UUID ≈ 142 字符，**超过 AF_UNIX socket 的 104 字节 sun_path 上限**——hermes 的 `_fits_sun_path` 防护静默跳过长候选、退回 `$TMPDIR`。
**修复**：socket 锚点改用规范短路径 **`/run/user/<uid>/pilibala-ai`**（≈68 字符、0700 私有、随用户会话存续；叶子 `hermes-gw-<home哈希>` 天然区分不同 home，锚点刻意跨 grant 共享）。
**验证**：daemon socket 实测落在 `/run/user/1000/pilibala-ai/hermes-gw-6c0ee542…/control.sock`。

### 3. 推理参数（effort）记录毒化：乐观传递 + 已验证降级（已修复）
hermes-acp 对 `session/set_config_option` 回答**空** `configOptions` 列表；acpx 把空数组当作有效结果写入持久会话记录，之后每次 resume 在能力断言处死亡。
**修复（acpx 0.12.0 补丁，双向）**：写侧——空 configOptions 不再写入记录（空 = 未通告，非约束）；读侧——已存在的空列表按透传处理（**已中毒记录透明自愈**）。
**设计原则（用户定案）**：ACP 协议支持传递推理参数且多数模型支持高推理档位——**乐观发送，仅当模型确实不支持且交互失败时才降级**；永远不预移除参数。失败时的 try/catch 降级（记录日志、继续用后端默认）保持不变。

### 4. home 生命周期与凭据刷新解耦（本版核心策略）
受管 home 从 per-run 一次性（mkdtemp）改为**每 grant 持久化**：~1.2GB 的 harness 引导每个凭据作用域只跑一次；凭据本身仍每 run 刷新（epoch 守卫）；API-key 运行结束后保留 home（其中无凭据材料，key 走 run 环境）。
配套：
- `execute.ts` 预置宿主 checkout 符号链接 + 一次性 `hermes pm repair`，借用启动跳过依赖重装；
- 凭据经 **provider 作用域环境变量**（`PILIBALA_<PROVIDER>_KEY`）+ 配置 `model.key_env` 指针投递（hermes 会从终端子进程剥离 OPENAI_API_KEY 等已知键）；
- UI：composer 对 hermes_local acp agent 显示实际引擎名（"Hermes ACP"）。

## 二、升级步骤

1. 拉取本版并重启 dev 服务（**必须完整重启**：acpx 补丁在 node_modules，tsx watch 不重载）：
   ```bash
   git pull && systemctl --user restart paperclip-dev
   ```
2. 已中毒的旧会话记录**无需手工清理**：读侧守卫使空列表透传，首个 run 自动恢复；记录上的 reset 标记（如有）会触发一次 fresh bootstrap（有界 handoff 重建上下文）。
3. agent 的 `adapterConfig.effort` 可正常设置——乐观传递，不再毒化；个别模型确实不支持时运行内降级并记录日志。

## 四、已知问题（不阻塞本版）

| # | 问题 | 状态 |
|---|---|---|
| 1 | repair/teardown 的 close 路径 spawn env 与主路径不同源（`Failed to spawn agent command: hermes-acp`）；close 为尽力而为，discard gate 已兜底 | 记录在案，后续统一 close 路径 env |
| 2 | 持久 home 被清理分支删除时对引用它的会话记录**静默**（无级联失效广播） | 记录在案（设计规范 P6：删除必须广播失效） |
| 3 | `buildHermesAcpConfig` 中"为 nvidia/ 模型自动设置 managedAiRouting"的块：对当前全部受管 agent 惰性，但对"无 connection 且 nvidia/ 模型"的未来 agent 会构造无凭据路由 | 建议下版删除或加凭据存在性检查 |
| 4 | deepseek-v4.1-flash 在 NVIDIA 端点对请求报 Invalid request（provider 层，与模型/参数组合相关） | 待 provider 层探针定位 |
| 5 | reasoning effort 在 hermes-acp 上"接受但不应用"（上游交付缺口）；生效通道为 Hermes 侧 provider/model 配置（boot 时应用） | 上游反馈 + 现有通道文档化 |

## 五、设计规范（本版确立，后续版本遵循）

| # | 规范 | 一句话 |
|---|---|---|
| P1 | 生命周期所有权 | 共享资源的路径与生命周期由其最长生命周期消费者决定 |
| P2 | 键分层 | 重状态按最粗安全粒度（harness 池）；轻状态按最细行为粒度（凭据/用户）；任务上下文按 run |
| P3 | 失效协议 | 跨键引用必须读侧容忍 + 写侧复位；删除必须广播失效 |
| P4 | 能力阶梯 | 可选参数统一：乐观发送 → 验证失败 → run 内降级 → 按作用域持久跳过 → 配置变更清除 |
| P5 | 爆炸半径对称 | 只共享与凭据无关之物；承载身份/状态的进程永不跨凭据共享 |
| P6 | 清理属主 | run 级清理只拥有 run 级路径；基座清理必须发失效事件 |
| P7 | 版本演进 | 借用环境与宿主版本演进必须钉住或显式再验证 |
| P8 | 可观测性 | 工件自识别（manifest），规模下不依赖 /proc 取证 |

## 六、回滚

`git revert` 本提交并重启即可回到 0.0.10 行为；持久 home 目录（`/tmp/pilibala-ai-*`）可安全删除——首个 run 会重新引导。
